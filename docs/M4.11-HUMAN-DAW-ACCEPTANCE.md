# M4.11 — Human DAW Acceptance

Status: **PREPARED — REAL-DAW HUMAN SESSION PENDING**

## Purpose

M4.11 proves that the already-accepted Resonant Engine VST3 wrapper behaves
correctly inside one real DAW and still sounds like the frozen M3 Breath Pipe
Reference Voice.

This is a human acceptance gate, not a new synthesis or architecture slice.
M4.11 must not retune the Breath Pipe, add a second DSP path, or weaken the M3
B01–B18 baseline to accommodate host behaviour.

## Reproducible preparation

Run from a clean Windows clone:

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\m4_11_windows\prepare.ps1
```

The script:

1. requires a clean Git working tree;
2. records the exact Git head;
3. configures the pinned VST3 SDK build with warnings-as-errors;
4. builds the complete Release tree, including
   `ResonantEngineBreathPipe.vst3`;
5. runs the repository CTest suite;
6. locates the generated VST3 bundle;
7. writes a deterministic per-file SHA-256 plugin manifest;
8. writes machine/session metadata and a pre-populated human acceptance record.

By default it does **not** modify the system VST3 directory. To copy a fresh
bundle into the standard VST3 location:

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\m4_11_windows\prepare.ps1 -Install
```

The install option refuses to overwrite an existing
`ResonantEngineBreathPipe.vst3` bundle. Replacing an existing bundle must be a
deliberate separate action rather than an implicit side effect of preparation.

## Frozen voice-allocation expectation

The current M4 VST3 reference wrapper contains one
`Engine<BreathPipeVoice>` and therefore one active synthesis voice.

M4.11 does **not** claim the M3 Lab four-voice allocator is present in the VST3
wrapper. The human host gate instead requires sane monophonic behaviour:

- a newly played overlapping note takes control predictably;
- releasing an older/non-active note must not create a stuck or runaway state;
- releasing the active note must allow the instrument to return safely;
- chords/retriggers must remain bounded and must never crash, explode
  numerically or leave an unrecoverable sounding voice;
- transport stop/restart and plugin reload must recover to known-good state.

Future VST3 polyphony would be a separately scoped implementation decision.

## Human execution record

Do not mark a test PASS from automated evidence alone. The listener/operator
must directly observe the DAW behaviour.

### H01 — Plugin scan and load

1. Rescan VST3 plugins in the DAW.
2. Confirm `ResonantEngineBreathPipe` is discovered.
3. Instantiate it on an instrument channel.
4. Confirm the DAW remains responsive and the plugin reports no load error.

PASS requires a clean scan and successful instance creation.

### H02 — Accepted Breath Pipe playback

At 48 kHz, play sustained notes around A3/C4 and across a wider part of the
accepted C2–C6 range.

PASS requires:

- clearly audible Breath Pipe output;
- no unexpected silence, DC-like failure, denormal runaway or obvious host
  corruption;
- pitch movement follows played notes coherently.

### H03 — Velocity response

Play the same note at low, medium and high velocities.

PASS requires velocity to produce a clearly audible expressive/energy change.
It need not be a simple gain change; the frozen model intentionally maps
pressure/energy into interacting excitation behaviour.

### H04 — Expressive automation

While sustaining a note, automate at least:

- Pressure;
- Timbre;

and one of:

- Turbulence;
- Interaction;
- Damping;
- Regeneration;
- Feedback colour;
- Nonlinear drive.

PASS requires smooth, audible, coherent response without stepping, host errors,
stuck state or numerical runaway.

### H05 — Overlap/chord/retrigger behaviour

Perform this deterministic overlap check:

1. hold C4;
2. while C4 remains held, play E4;
3. release C4 while E4 remains held;
4. release E4;
5. play a short C4–E4–G4 chord and several rapid retriggers;
6. stop transport / send all-notes-off if the host provides it.

PASS requires bounded monophonic behaviour with no crash, permanent silence,
unrecoverable stuck note or runaway output.

### H06 — Project state save/reopen

1. Set several persistent parameters to clearly non-default values.
2. Save the DAW project.
3. Close the project/DAW sufficiently to destroy the live plugin instance.
4. Reopen the saved project.
5. Verify the parameter values are restored.
6. Verify no transient note is resurrected merely because the project was
   loaded.
7. Play a fresh note and confirm normal output.

PASS requires deterministic persistent parameter/model recall and clean
transient-state reset.

### H07 — Offline bounce

Create a short arrangement containing notes plus visible automation and render
it using the DAW's offline/export path.

PASS requires:

- a non-empty audio file;
- expected note/automation content is audible;
- no missing render caused by offline process mode;
- no non-finite/runaway output.

Record the bounce filename, format, sample rate, file size and SHA-256.

### H08 — Stop/start/reload recovery

Exercise repeated:

- transport stop/start;
- note retrigger;
- plugin disable/enable where supported;
- project close/reopen or plugin instance reload.

PASS requires the instrument to recover without stuck or runaway state.

### H09 — M3 identity / no-material-change listening gate

The final listener gate is comparative.

Use the accepted M3 Breath Pipe Lab/B-series reference as the sonic baseline.
At minimum compare:

- stable-pipe character;
- pressure response;
- expressive timbre movement;
- pitch/register character;
- aggressive/high-energy recovery where practical.

The exact M3 B01–B18 suite remains the authoritative reference; M4.11 does not
replace it with a new taste test.

PASS wording:

> The real DAW host does not materially change the accepted M3 Breath Pipe
> identity or expressive behaviour.

If the listener hears a material difference, record **FAIL** and the perceived
difference before making any DSP change.

## Overall acceptance rule

M4.11 passes only when all are true:

- H01–H08 are direct real-DAW PASS;
- H09 listener verdict is PASS;
- tested Git head and plugin manifest are recorded;
- DAW/OS/audio configuration is recorded;
- no source/DSP change occurred during the session;
- any bounce evidence is retained with a hash.

A crash, scan failure, persistent state loss, silent offline bounce, stuck
voice, runaway state or listener material-difference verdict is blocking.

## Failure policy

Do not respond to a human-host failure by immediately retuning the Breath Pipe.

Classify first:

1. build/package/install problem;
2. DAW scan/registration problem;
3. event/automation translation problem;
4. state/lifecycle problem;
5. offline-render problem;
6. genuine host-induced DSP/timing difference.

Only category 6 can justify revisiting accepted DSP, and doing so would require
an explicit superseding decision rather than an incidental M4.11 patch.

## Completion boundary

M4.11 may be marked accepted only after the real DAW session evidence is
reviewable.

Repository preparation, automated tests, validator results and generated
manifests can establish that the candidate is ready for human testing. They
cannot substitute for the listener/operator verdict.
