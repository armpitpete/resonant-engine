## Canonical architecture walk

### Pressure

PASS. Pressure is defined as a continuous driving-force concept in the Sonic Design Contract and is not tied to MIDI, amplitude or one Host API. M0.7/M0.8 must preserve sample-accurate event/parameter delivery for it.

### Turbulence

PASS WITH DEFERRED IMPLEMENTATION. Turbulence is a first-class excitation concept rather than a cosmetic noise layer. Deterministic portable random/noise behavior is explicitly required later by M0.12.

### Continuous excitation

PASS. The architecture does not require note-on or a conventional oscillator. A model can receive/driven excitation every sample.

### Transient excitation

PASS. The Sonic Design Contract treats impulses, strikes, plucks and finite bursts as valid excitation alongside continuous flow.

### Exciter reaction to resonator state

PASS. The generic model owns internal topology, so returned resonator state may affect a future exciter. M0.9 must make this compatibility explicit in the formal interfaces.

### Passive resonator

PASS. Nothing in `resonant_core` requires active energy injection. Passive loss/decay is part of the normative model vocabulary.

### Regenerative resonator

PASS. Feedback is preserved as in-model topology rather than a Host effect.

### Self-sustaining resonator

PASS. Active energy balance is not prohibited. M0.10/M0.11 must define feedback and stability behavior without forbidding self-sustaining regimes.

### Controlled instability

PASS. Musical instability is explicitly distinguished from numerical failure. Future diagnostics must detect numerical runaway without forcing musically unstable states to be suppressed.

### Feedback filtering

PASS. Filtering is allowed inside the returned-energy path and must not be reduced to post-output tone shaping.

### Nonlinear feedback

PASS. Nonlinearity is allowed structurally inside feedback. Later oversampling/alias-control choices remain implementation work.

### Sample-accurate movement

PASS ARCHITECTURALLY. Host blocks do not define internal feedback timing. M0.7/M0.8 still have to prove sample-accurate events and parameter changes formally.

### Continuous pressure movement

PASS ARCHITECTURALLY. Pressure is a continuous concept and Host wrappers are forbidden from becoming the only place essential smoothing/dynamics can occur.

### Overblow-like transitions

PASS. No abstraction forces one oscillator, one mode or one fixed register. Future resonators may reorganize mode/register/state as excitation changes.

### Tuning reacting to phase changes

PASS WITH DEFERRED RESONATOR DESIGN. The core does not require fixed integer-delay tuning or one oscillator abstraction. Fractional-delay, modal, waveguide or hybrid approaches remain possible. M0.9/M0.10 must preserve tuning/feedback phase interaction.

### Energy observation

PASS ARCHITECTURALLY, IMPLEMENTATION DEFERRED. Diagnostics output is part of the M0.4 core boundary. M0.11 must define operational energy metrics and Host observation.

### Runaway detection

PASS ARCHITECTURALLY, IMPLEMENTATION DEFERRED. The core reserves bounded diagnostics. M0.11 must define finite-state/runaway detection and optional containment.

### Arbitrary audio excitation

PASS. M0.4 explicitly reserves caller-owned external audio input without allowing the core to open files, microphones or network sources itself.

### Resonator as future exciter

PASS. The generic boundary does not type-restrict excitation to a noise generator or note source. M0.9 must formalize compatibility.

### Bidirectional resonator coupling

PASS. Coupling is a normative concept and future resonator graphs are protected by the architectural invariants.

### Future graph topology

PASS. M0 does not implement arbitrary graphs, but the core/model boundary does not make Host wrappers owners of topology. M0.9/M0.10 must avoid contracts that assume a permanently linear one-resonator chain.

### WASM/browser host

PASS AT ARCHITECTURE LEVEL. Core interfaces use portable C++/memory concepts and no browser/Web Audio types. M0.17 still must prove WASM/AudioWorklet feasibility.

### VST3 host

PASS AT ARCHITECTURE LEVEL. VST SDK/JUCE types are prohibited inside the core. A wrapper can translate Host buffers/events/parameters. M0.17 still must prove wrapper feasibility.

### Embedded host

PASS AT ARCHITECTURE LEVEL. No OS/filesystem/GUI/device API is required by the DSP boundary. M0.17 still must review ARM, memory, stack and CPU constraints.

### Steampipe special-case leakage

PASS. The generic core contains no Steampipe-named type, control or mandatory algorithm. Pressure/turbulence/resonance/feedback/nonlinearity are general synthesis concepts justified by Resonant Engine's own sonic contract.

## Host/block feedback proof

The current `ReferenceFeedbackProbe` demonstrates one important architectural property only:

> A Host can deliver a block while the model executes returned-energy interaction sample by sample inside that block.

It is deliberately **not** the final Engine, event, parameter, exciter or resonator API.

## Hostile review

The early architecture was attacked on the assumption that the future Breath Pipe would need capabilities the current provisional work had accidentally excluded.

### Weakness W1 — wrong language baseline

**Finding:** the first provisional branch used C++17 even though the canonical M0 plan specifies C++20.

**Severity:** blocking documentation/build contradiction.

**Fix:** CMake and the Product & Scope Contract now specify C++20.

**Result:** fixed.

### Weakness W2 — wrong M0.1–M0.4 interpretation

**Finding:** the first provisional notes treated M0.1–M0.4 as a narrower code-foundation slice, conflicting with the canonical section titles and task list.

**Severity:** blocking roadmap/state ambiguity.

**Fix:** M0.1–M0.4 have been realigned to Product & Scope, Sonic Design, Terminology and Portable DSP Core Boundary. Canonical documents now cover the complete supplied checklists.

**Result:** fixed.

### Weakness W3 — probe could accidentally harden into final API

**Finding:** `Engine<Model>::processBlock(Input*, Output*)` is useful as a feedback proof but too model-specific to stand as the final Host API for audio buffers, sample-offset events, parameters, external audio and diagnostics.

**Severity:** blocking only if treated as frozen API.

**Fix:** documentation now marks the current Engine/feedback types as probes. M0.6–M0.9 are explicitly authoritative for final processing/event/parameter/exciter/resonator interfaces.

**Result:** fixed architecturally; later contracts still required.

### Weakness W4 — turbulence has no deterministic primitive yet

**Finding:** the architecture requires turbulence but the branch has no canonical deterministic PRNG/noise primitive.

**Severity:** not an early-architecture blocker; mandatory later M0 work.

**Required action:** M0.12 must choose deterministic PRNG/seed behavior; M0.9 must allow deterministic seed input where relevant.

### Weakness W5 — energy/runaway observability not implemented yet

**Finding:** the early core only reserves diagnostics conceptually.

**Severity:** not an early-architecture blocker; mandatory later M0 work.

**Required action:** M0.11 must define energy/stability metrics, finite-state detection and Host observation.

### Weakness W6 — no resonator tuning/phase implementation yet

**Finding:** no current DSP algorithm proves overblow or feedback-filter/tuning phase interaction.

**Severity:** expected at M0; not an architecture blocker.

**Required action:** M0.9/M0.10 must avoid interfaces that prevent continuously retunable waveguide/modal/delay/hybrid resonators. Actual sonic proof belongs after M0.

## Repeat review after blocking fixes

The two blocking inconsistencies found by the hostile review—C++17 and incorrect M0.1–M0.4 interpretation—are fixed.

No remaining M0.1–M0.4 architecture choice requires a special pipe engine, Host-specific DSP, a mandatory oscillator, one-block feedback delay, output-only nonlinearity or note-trigger-only excitation.

## Continuum gate

Architecture walk:

- **silence** — allowed; no hidden oscillator requirement;
- **faint air** — allowed through continuous low-energy excitation;
- **turbulence** — allowed independently of stable pitch;
- **emerging pitch** — allowed as resonator organization strengthens;
- **unstable resonance** — allowed while numerical state remains finite;
- **stable pipe** — allowed by tuned resonator behavior;
- **rich pipe** — allowed through stronger interaction/feedback/nonlinearity;
- **overblow** — no fixed-register abstraction prevents it;
- **aggressive resonance** — active/nonlinear high-energy regimes are allowed;
- **noise** — pitch may collapse back toward turbulence/irregular behavior without an architecture change.

**Result: M0.1–M0.4 do not prevent any part of the required continuum.**
