# M0.21 — Early Breath Pipe Architecture Review

Status: **EARLY REVIEW PASS — with preserved requirements**

This review is intentionally being performed before the rest of M0 hardens the architecture.

## Protected future reference voice

```text
Pressure + Turbulence
        ↓
Exciter interaction
        ↕
Tuned resonator
        ↺
Active feedback
        ↓
Feedback filtering
        ↓
Nonlinearity
        ↺
```

Required future continuum:

```text
silence
→ faint air
→ turbulence
→ emerging pitch
→ unstable resonance
→ stable pipe
→ rich pipe
→ overblow
→ aggressive resonance
→ noise
```

## Review question

Can the M0 foundation support this signal behavior without replacing its central processing model later?

## Result

**Yes, provisionally.**

The sample-owned model loop is compatible with the Breath Pipe requirements because the host does not own the internal topology. A future Breath Pipe model can calculate pressure/turbulence excitation, consume returned resonator state, modify the interaction, pass energy through tuned resonant state, filter the returned path and apply nonlinear behavior within a single continuous real-time loop.

## Requirements that must remain protected

### 1. Continuous excitation is first-class

The architecture must never assume that sound exists only after note-on. Pressure and turbulence must be able to exist below pitched oscillation and continue while pitch stability changes.

### 2. The exciter must be interactive, not a one-way source

The future exciter must be able to respond to returned resonator energy. A fixed `noise -> filter -> resonator` chain is insufficient for the reference voice.

### 3. Feedback must exist inside the model

The feedback path cannot be implemented only as a host graph connection or one-block delay. Its timing and state belong to the physical/resonant model.

### 4. Resonance must not be reduced to an oscillator abstraction

A tuned resonator may later be a waveguide, modal structure, delay network, coupled structure or hybrid. The generic core must not require oscillator semantics.

### 5. Feedback filtering and nonlinearity are structural

They are not merely output effects. The future model must be free to place filtering and nonlinear interaction inside the returned-energy path.

### 6. Control must be sample-continuous

Pressure, turbulence, interaction strength, tuning, damping, feedback, filtering and nonlinearity may need smooth continuous movement. Host block size must not define control resolution.

### 7. Instability must be representable but bounded operationally

The engine must permit regimes that sound unstable, bifurcate, overblow or become noise-like. At the same time, numerical runaway, NaN/Inf propagation and unbounded host output are not acceptable.

### 8. Silence and faint air are real states

The design must not force a minimum pitched resonance or hidden oscillator floor. The continuum must genuinely include zero-energy silence and sub-pitched airflow/noise states.

### 9. Pipe controls stay out of the generic engine

`Pressure`, `Turbulence`, jet/reed behavior and overblow logic belong to the future Breath Pipe model. The portable engine supplies lifecycle, timing and processing only.

## Failure patterns to reject during later M0 sections

Reject an architectural change if it would require any of the following for Breath Pipe:

- a separate DSP engine from the one used by other resonant models;
- host-specific code in the resonant model;
- one-block feedback latency imposed by the engine;
- a mandatory oscillator as the pitch source;
- output-only distortion standing in for loop nonlinearity;
- note-on as the only way to create excitation;
- block-rate-only control of pressure/turbulence or feedback;
- heap allocation or locks in the audio process path.

## Early review verdict

**PASS.** M0.1–M0.4 may proceed on the current architecture.

The pass is conditional on preserving the requirements above through M0.5–M0.20. M0.21 must be repeated as the formal late-stage review before the M0.22 completion gate.
